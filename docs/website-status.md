## What works today

Run it:

```bash
cd web
npm install
npm run dev
```

Pick **Los Padres**, press **Run placement**. You get the region's real risk field and, within a second or two, ~572 sensor nodes placed by the team's own siting algorithm running live in the browser — alongside a head-to-head benchmark against a uniform grid.

The Lab now exposes the model's actual parameters as live controls: both drive weights, detection radius, coverage target, budget mode (saturation / auto / fixed) and a spacing override. Everything recomputes in a worker on every run, including the risk field itself — the browser recombines it from baked components rather than fetching a pre-combined raster, so moving a weight visibly moves the field, not just the nodes.

All eight regions are listed. The seven without committed data are disabled and say why: the siting model runs on any box on Earth, and what is missing is the offline bake, not the algorithm.

| Reported | Value |
|---|---|
| Blue-noise candidates | 927 |
| Nodes after greedy set cover | 572 |
| Hardware saved by minimisation | 38% |
| Risk-weighted coverage | 95.0% |

**Those are not approximations.** The TypeScript reproduces `place.py` bit-for-bit on the baked Los Padres data — identical candidate count, identical 572-element selection sequence, identical coverage scalars to all 15 digits — and it has been verified at **every one of the 46 detection-radius slider positions**, not just the default.

## What is verified, and how

Parity is the site's central claim, so it is defended by tests rather than by assertion.

- **The whole algorithm is ported and pinned.** Blue-noise sampling, greedy set cover, coverage measurement, demand sampling, the local projection, and field sampling all reproduce the Python against committed golden fixtures generated by running the real `place.py`.
- **The random generator is shared.** `place.py` takes its generator as an argument, so a small, fully-specified generator (xoshiro256\*\*) implemented identically in Python and TypeScript gives byte-identical streams — with no change to `place.py` and no need to port numpy's PCG64.
- **Eight deliberate mutations are caught by the suite.** Removing the float32 narrowing, the vertical raster flip, the coordinate-frame correction, the CELF tolerance, the hit-list sort, the summation alignment guard, the grid-shape search, or the pairwise summation all fail tests. Each was applied by hand and confirmed.
- **269 tests.** `cd web && npm test`.
- **Parity now covers the budgeted regime too.** `verify_parity.py` runs `plan_region`'s `auto` path as well as saturation, and the TypeScript pins 18 nodes, the derived 7.5552/18.4683 km spacing and a sha256 of the chosen sequence against it.

## Data provenance

`web/public/data/los-padres/` holds the baked model inputs. Regenerate with:

```bash
python -m tools.bake.bake_region --region los-padres
python -m tools.bake.bake_region --region los-padres --notes-only   # provenance text only
```

| Layer | Source |
|---|---|
| Land cover / fuel | ESA WorldCover v200, 2021 epoch, 10 m native — shipped at ~92 m × 111 m |
| Fire activity | NASA FIRMS (VIIRS 375 m + MODIS 1 km) |
| Fire weather | Canadian FWI from ERA5 via Open-Meteo |
| Imagery / terrain | MapTiler (presentation only, not a model input) |

`meta.json` carries the full provenance, including the caveats: the risk field is renormalised to its own peak (so values are **not** comparable between regions), the FIRMS count uses a 0.25° pad and is an upper bound on what reaches the model, and the FWI values are not operational-scale.

## Known limits — read before writing any copy about this

**The two Python systems do not cover the same ground.**

- The **siting model** is genuinely global. Any bounding box on Earth.
- The **fire-spread model** is **California only** — it is built on CAL FIRE FRAP perimeters and LANDFIRE rasters, and LANDFIRE is CONUS.

So detection-time claims can only be made where the fire model is validated. It is validated against two real California fires, which is a strong and specific claim. Stretching it worldwide is the kind of overreach that collapses in Q&A.

**The model does not use elevation or camper traffic.** The risk field is `flammability × (base + weather + activity)`. Both are marked as roadmap, not implemented.

**Only Los Padres is baked.** The other seven regions are defined upstream but have no data committed; the picker says so rather than failing.

### Benchmark A, measured

At **equal realised node count**, on the same 31,045 demand points, risk-weighted, at a 0.366 km scoring stride and a 2.0 km detection radius:

| Node budget | scored | risk-driven | uniform grid | Δ |
|---:|---:|---:|---:|---:|
| 50 | 45 | 12.69% | 10.96% | **+1.74 pp** |
| 132 | 124 | 33.44% | 29.89% | **+3.55 pp** (widest lead) |
| 215 | 193 | 49.46% | 46.57% | +2.88 pp |
| 351 | 311 | 71.51% | 74.49% | −2.98 pp |
| 572 | 526 | 92.76% | 96.93% | −4.17 pp |

**The lead changes hands at 285 nodes** — bisected between the 215 and 351 samples, not read off the sampled ladder. Risk-driven siting wins where the budget is
tight — which is the situation the product is actually for — and a uniform grid wins
once you can afford to blanket the ground. Reporting only one end of that curve would
be a cherry-pick, so the site reports the curve.

The baseline is given the burnable mask on purpose: that hands it part of the model's
own input and makes it stronger. An unmasked grid scores 98.4% at 572 requested but
wastes nodes on the Pacific.

## The lightning pivot, measured

The risk field's third term is no longer "where fire has recently been". On James Bay it is **strike density** from the NASA LIS/OTD climatology — where ignition is likely. One raster swapped; the recombination arithmetic is byte-identical, and the bit-for-bit parity test now runs on both regions.

**The resolution the spec got wrong.** LIS/OTD HRFC is 0.5° (~55 km), not the 0.1° the spec claimed. The 0.1° product is LIS-only and stops near ±38° of latitude, so it does not exist for any boreal region; at 51–53 °N even the combined product is OTD alone (1995–2000). That is **40 native cells for a 314 × 244 km box** — a regional gradient and nothing finer, with per-cell Poisson error around 40%. Upsampling is interpolation, not resolution.

**The gradient gate, run before the bake, on observed flash counts:**

| quantity | value |
|---|---|
| observed OTD flashes | 218 over 40 cells |
| viewtime spread | 3.1% — counts compare directly |
| against a uniform rate | χ² = 118.1 / 39 dof, p = 6.8 × 10⁻¹⁰ |
| inland half vs coastal half | 143 vs 75 — **1.91×**, p = 4.8 × 10⁻⁶ |
| Spearman ρ with longitude | 0.469, p = 0.0022 |

The region was chosen on the hypothesis that a coast gives land–water convective contrast and therefore real spatial structure. It does, and it is significant. Had it come back flat, the bake would have printed "decorative" and the source notes would have said so — the gate exists to be able to fail.

### Benchmark C: coverage that needs two towers

A single tower gives a fix; two give an intersection. At the shipped defaults (james-bay, 15 km confirmation radius, 13,676 demand points, 1.41 km stride):

| rule | risk-driven | uniform grid | Δ at the budget | grid takes the lead at |
|---|---:|---:|---:|---:|
| one tower in range | 77.3% | 78.8% | −1.4 pp | 88 towers |
| two towers in range | 10.9% | 7.0% | **+3.9 pp** | never, in this range |

Same 111 towers, same demand points, one rule changed, and the sign of the margin flips. A lattice spaces to avoid overlap; overlap is the product here.

**The prediction was that the margin would be wider under the two-tower rule. It is not** — the peak is 3.93 pp against single coverage's 5.56 — and that comparison turned out to be meaningless, because the double-coverage margin is still climbing at the largest budget measured. The page leads with 10.9%, not with the margin: a network sized to hear every strike once triangulates about a tenth of its own region, and a favourable comparison on a small number is still a small number.

The risk-driven arm is also being scored on an objective it never optimised — `greedyMinimise` minimises single coverage — so +3.9 pp is a floor.

## Bugs found in the upstream Python

Recorded in `docs/repo-issues.md`, none fixed here — the website work is additive and no repo-root Python has been modified. The two that matter most:

- **`plan_region` exports every node half a bounding box out of position** (41.18 km east, 33.40 km north on Los Padres) because corner-origin kilometres are fed into a centre-origin frame. Coverage statistics are unaffected; the geography is wrong in every GeoJSON published from it.
- **`place.py`'s seeding is not reproducible** across numpy builds, because `np.argsort` is unstable and ties are the *normal* case on real data — with no FIRMS detections in a box, risk is exactly 1.0 at every tree and shrub pixel.
